# Wijhan Backend

Laravel + MySQL API backend for the [Wijhan](https://wijhan.com) marketing
site: contact/quote lead capture, public content endpoints, and an admin
API for managing leads. Built to sit behind the existing TanStack Start
frontend (`../business-first-engineering`), which this repository does not
modify — see `INTEGRATION.md` for how to wire the two together.

See `API.md` for the full API reference.

## Requirements

- PHP 8.2+
- Composer
- MySQL 8+ (MariaDB 10.4+ also works)

## Installation

```bash
composer install
cp .env.example .env
php artisan key:generate
```

Edit `.env`: at minimum set `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` to
match a MySQL database you've created (`CREATE DATABASE wijhan_backend;`),
and `FRONTEND_URL` to the origin(s) the frontend is served from.

```bash
php artisan install:api   # only needed if starting from a bare Laravel install
php artisan migrate
php artisan db:seed
```

Seeding creates:
- An admin and a manager account (`ADMIN_SEED_EMAIL`/`ADMIN_SEED_PASSWORD`,
  `MANAGER_SEED_EMAIL`/`MANAGER_SEED_PASSWORD` in `.env` — change the
  defaults before using anything but a local database).
- The six services, three pricing plans, and project categories that
  already exist in the frontend's `src/lib/site-data.ts` / `site-data-ar.ts`
  / `src/routes/pricing.tsx`.

## Running locally

```bash
php artisan serve
```

Mail is queued (`QUEUE_CONNECTION=database`) so a mail-provider outage
never fails a lead's HTTP request. For queued mail to actually be
delivered, run a queue worker alongside the server:

```bash
php artisan queue:work
```

With `MAIL_MAILER=log` (the default), queued emails are written to
`storage/logs/laravel.log` instead of actually being sent — switch to
`smtp` (or another real driver) in `.env` for real delivery.

## Tests

```bash
php artisan test
```

Tests run against an in-memory SQLite database (configured in
`phpunit.xml`) and never touch the real MySQL database or send real email
(`MAIL_MAILER=array`, `QUEUE_CONNECTION=sync` in the test environment).

## Production

Development deliberately runs **without** Laravel's cached bootstrap files,
so config/route/view changes are picked up immediately. If a cache was
generated by accident, clear it:

```bash
php artisan optimize:clear
```

Only on the production server (never in development), after every deploy:

```bash
composer install --no-dev --optimize-autoloader
php artisan migrate --force
php artisan optimize            # caches config, routes, events and views
php artisan filament:optimize   # optional: caches Filament components/icons
```

Production checklist:

- `APP_ENV=production`, `APP_DEBUG=false`, a real `APP_URL`, and `FRONTEND_URL`
  set to the real site origin(s) only.
- A real mail driver (`MAIL_MAILER=smtp`, …) and a supervised
  `php artisan queue:work` process.
- Use `docker/php/php.ini` (`expose_php=Off`, production OPcache) as the PHP ini of the production image.
- PHP **OPcache enabled** (`zend_extension=opcache`, `opcache.enable=1`).
  In production also set `opcache.validate_timestamps=0` and restart PHP-FPM
  on each deploy. For the local `php artisan serve` dev server,
  `opcache.enable_cli=1` is also required for it to apply.
- With `config:cache` active, `env()` is only read inside `config/*.php` —
  re-run `php artisan optimize` after any `.env` change.

## Project structure

```
app/
├── Enums/            ContactStatus, QuoteRequestStatus, AdminRole
├── Http/
│   ├── Controllers/  Public + Admin controllers
│   ├── Requests/      Form Request validation
│   └── Resources/     API Resource transformers
├── Mail/              Team notifications + client confirmations (EN/AR)
├── Models/
├── Policies/          ContactPolicy, QuoteRequestPolicy
├── Services/          ContactService, QuoteRequestService
└── Support/           EngagementOptions (shared project_type/budget_range values)
database/
├── migrations/
├── factories/
└── seeders/
routes/api.php
tests/Feature/
```

## Known limitations

- No CAPTCHA/Turnstile yet — only IP-based rate limiting. The route
  middleware stack is structured so one can be added without refactoring.
- `/work`'s case studies table exists but is intentionally seeded empty —
  the frontend itself currently states no verified project details have
  been supplied yet.
- Queued mail requires a running `queue:work` process (or a supervisor in
  production) to actually be delivered — it will sit in the `jobs` table
  otherwise.
